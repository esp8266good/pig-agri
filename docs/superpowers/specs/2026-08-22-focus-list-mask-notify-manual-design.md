## 1. 關注清單

### 1.1 判定演算法不動

異常判定的基準維持「同一台相機所有合格豬的活動量中位數」。

**否決**：把基準換成 top-N 平均（「跟最活潑的比落後多少」）。
理由是中位數對 MOT ID 跳號是穩健的；換成 top-N 平均之後，一隻軌跡被切碎又亂跳的豬
就足以把基準拉高，全欄跟著被標低。要動基準值得另開一輪實驗驗證，不與 UI 改版綁在一起。

「拿活動量最高的來做對照」因此純粹是呈現層的功能，不影響任何後端狀態。

### 1.2 三種標籤

關注清單的成員帶三種標籤之一：`異常`、`最低`、`對照`（定義見 `CONTEXT.md`）。

**否決**：人工釘選（pin）作為第四類。
理由是釘選必須綁在 `object_id` 上，而 `object_id` 因 ID 跳號並不穩定，
人工釘選的豬隔天可能對應到另一隻，製造的困惑比解決的多。等 ID 穩定性有把握再談。

### 1.3 顯示條件

- `最低` 只在該相機**完全沒有異常**時才顯示。有異常時清單只列異常。
  理由：有異常時「最低 N」幾乎必然與異常清單重疊，同時顯示會讓人分不清
  哪些是系統真的在告警。
- `對照` 顯示（除非 M = 0）。

**全欄活動量偏低時（2026-08-22 補）**：`analysis/scheduler.py` 既有的保護是
`herd_ok` 為假（合格豬的活動量中位數低於 `activity_abs_floor`，或合格豬少於 2 隻）時
整欄不做異常判定。關注清單跟著這條保護走：

| 情況 | 清單內容 |
|---|---|
| `herd_ok` 為假，且沒有未解除的舊警報 | 只顯示一行「豬群活動量普遍偏低，暫不評估」 |
| `herd_ok` 為假，但有豬還在 `alerted` | 只列那些警報，不附對照組 |
| `herd_ok` 為真 | 照 1.3 的規則走 |
| 重啟後第一輪分析尚未跑完 | 顯示「首次分析尚未完成，稍候再看」 |

最後一列是 2026-08-22 實機發現的：`scheduler._loop` 先 `sleep(interval)` 再分析，
`_rebuild_cache` 只建骨架不算活動量，所以重啟後最長一個 `analysis_interval`
（預設 30 分鐘）內 `herd_ok` 都還是預設的 `False`。不把這個狀態分開講，
使用者會在重啟後看到「豬群活動量普遍偏低」，被指向完全錯誤的結論。
cache entry 因此多一個 `analyzed` 旗標。

理由是清單的意義就是「現在該去看哪幾隻豬」，在沒有評估依據時給出名字，
等於把 scheduler 的夜間保護作廢。對照組在這個狀態下也一併不顯示：
從一群都在休息的豬裡挑「最活潑的」拿來當「正常長什麼樣」的參考點只會誤導。

⚠ 這個訊息**不能寫成「GPU 排程休息中」**：那是另一個狀態
（`gpu_off_schedule_enabled`，目前預設關閉），發生時完全沒有推論、
連豬隻清單都是空的。兩者混用會把使用者指向一個他根本沒開的設定。

為了讓 API 看得到這個狀態，`herd_ok` 每輪寫進 anomaly cache 的每個 entry
（per-camera 的判斷存在 per-object 的 entry 裡，沿用 `activity_mean` 的既有做法）。

### 1.4 版面位置與排序

關注清單放在現有「豬隻狀態」tab 的表格**上方**，作為獨立區塊；下面的完整表格行為完全不動。

**否決**：把置頂做成豬隻狀態表格本身的排序規則。
理由是它會跟現有的「點欄位標題排序」直接打架：使用者按了「活動量」排序之後，
置頂邏輯要不要蓋過他的選擇，兩個答案都是錯的。獨立區塊沒有這個矛盾。

**挑選邏輯放後端（2026-08-22 補）**：標籤與排序由 `focus_list.select_focus` 決定，
前端只負責畫。理由與 3.2 的折疊同一條：前端沒有測試框架，純函式寫在 JS 只驗得到語法；
挑選需要的資料（每隻豬的 `activity_current` 與兩個異常旗標）全都在後端的 anomaly cache 裡。
端點是 `GET /alerts/focus?camera_id=`，與豬隻狀態表格同源，兩邊的活動量因此一致。

**區塊內排序**：異常在前（同為異常時按活動量升序）→ 最低（活動量升序）→ 分隔線 → 對照。
對照組用分隔線隔開，因為它的意義與前兩類相反，混在同一個排序裡會誤導。

### 1.5 bbox 顯示模式

新增「只顯示關注清單的框」模式，**預設開啟**：

| 標籤 | 框的樣式 |
|---|---|
| 異常 | 粗紅框 + 現有的 ⚠ / 🌡 圖示 |
| 最低 | 橘框 |
| 對照 | 綠框 |
| 其他豬 | 不畫 |

這個過濾**只在 LIVE 生效**。回放沒有關注清單（那是「現在」的判斷），
在 VOD 濾掉非異常的框會讓沒有異常的時段整片空白，使用者分不出系統是不是壞了。

**否決**：異常之外一律不畫。
理由是零異常時畫面會完全空白，使用者無從判斷系統是正常運作還是掛了。
給最低與對照各自的顏色，畫面上永遠至少有幾個框，同時仍然乾淨。

**否決**：其他豬畫淡灰細框。理由是這等於沒有簡化畫面，功能的價值就消失了。

### 1.6 設定歸屬

| 設定 | 存放 | 預設 | 界限 |
|---|---|---|---|
| `focus_lowest_enabled` | DB（`user_settings`） | `true` | 布林 |
| `focus_lowest_n` | DB | `3` | 1–20 |
| `focus_top_n` | DB | `3` | 0–20，**0 表示關閉對照組** |
| 只顯示關注清單的框 | `localStorage` | 開 | — |
| 顯示遮罩範圍 | `localStorage` | 關 | — |

DB 的三項是「這個豬場要看幾隻」的營運決定，換一台平板看應該一樣，
而且存 DB 才走得到既有的 `_NUMERIC_BOUNDS` 值域檢查（上界 20 用來擋
「打 999 把整欄列出來」）。兩項 `localStorage` 是純視覺偏好，不同人可以不一樣。

`focus_top_n` 不另給啟用開關，用 0 表示關閉：少一個 key、少一處 UI，
且 0 在這裡沒有語意歧義。

## 2. 遮罩編輯器

### 2.1 語意：過濾偵測，不塗黑影像

遮罩**不改變任何影像**。detector 照常在完整畫面上跑，
輸出的偵測框若與任一啟用中的遮罩區域重疊面積**超過 60%**，就丟棄，不進 ReID、不進 tracker。

**否決**：把 `rgb_np` 的遮罩區填黑再送進 detector。
理由有二：塗黑會製造一條假的高對比邊緣，YOLO 有機會在邊界產生新的假偵測；
遮罩區旁邊的真豬會少掉一部分身體的視覺 context，ReID feature 跟著變髒。
省下的計算量不是這裡的目標，不製造新的錯誤才是。

**否決**：只看 bbox 中心點是否落在遮罩內。
理由是一隻豬走到遮罩邊界會閃爍進出，把軌跡切碎，而軌跡完整性直接決定活動量的正確性。

**60% 這個門檻寫死，不做成設定**。它是一個沒人有直覺的數字，開放出來只會被亂調
然後回報「遮罩壞了」。需要調整時改常數重啟，成本比維護一個沒人會用對的設定低。

### 2.2 過濾插入點

`inference/pipeline.py:_process_batch`，在 detector 輸出之後、
ReID feature 抽取（現行 `:258`）之前。放在這裡順便省掉被丟棄那些框的 feature 抽取。

### 2.3 已知副作用（寫進手冊，不需修正）

豬走進遮罩區時偵測消失 → `max_age=300` 幀撐約 30 秒 → 進失蹤池（`lost_track_buffer=1200`
幀約 120 秒）→ 走出來由 ReID 以 `reid_revive_thresh=0.3` 接回原 `id`。
這是既有機制，會正常運作。代價是那段空窗在活動量上呈現為一次大跳躍的位移。

⚠ **不要用遮罩去遮豬會頻繁進出的區域**。遮走道、遮飼料槽外側、遮鏡頭邊角照到的隔壁欄
不受影響；遮一塊豬會進進出出的地方會製造大量假的位移跳躍，污染活動量。這條要寫進手冊。

**2026-08-22 現場確認**：實際要遮的只有走道與牆壁，豬不會進出這些區域，
因此上述副作用在本場域不適用。這也表示未來若要新增遮罩區域，
必須先確認該區域不是豬會進出的地方，否則這個設計要重做。

### 2.4 幾何與儲存

**多邊形**，每台相機可有多個區域。

**否決**：只做矩形。理由是要遮的通常是走道、飼料槽、鏡頭邊角的隔壁欄，
這些都不是矩形，用矩形會連帶遮掉一大塊真的要看的地方。

**儲存**：新開一張 `camera_masks` 表，每列一個區域，欄位至少包含
`camera_id`、`label`、`enabled`、`points`（正規化 0..1 的頂點序列）。

**否決**：塞進 `user_settings` 的扁平 key-value。
理由是遮罩是「每台相機一組區域」的結構化資料，硬塞成 JSON 字串會讓既有的
`_NUMERIC_BOUNDS` 值域檢查完全用不上，等於自己寫一套平行的驗證。

新表的額外好處：每個區域可獨立 `enabled` 與命名（「走道」「隔壁欄」），
出問題時可以單獨關掉一塊來二分定位。

座標存正規化 0..1，相機解析度換了不用重畫。

### 2.5 生效路徑

存檔時由 router 直接呼叫 `inference_pipeline.set_masks(camera_id, regions)`，
照 `routers/settings.py:201` 的 `_RELOAD_KEYS` → `scheduler.reload(...)` 先例。

**否決**：pipeline 每 N 秒自己查 DB。
理由是 pipeline 跑在自己的 thread、不是 async context，要查 DB 得另接一條 async 橋；
而寫入頻率是一天幾次、讀取是每秒十次，push 明顯划算。

app 啟動時從 DB 讀一次載入。

### 2.6 編輯器的底圖與疊圖

**底圖**：從正在播放的 `<video>` element `drawImage` 到 canvas，純前端，不加端點。

**否決**：新增 `/stream/{camera_id}/snapshot`。
理由是 live 頁本來就在播，抓一幀是幾行程式；加端點反而要處理「相機斷線時回什麼」。

**live 疊圖**：遮罩區平常**不顯示**。遮罩正常運作時使用者不需要看到它，
一直蓋著半透明色塊只會干擾看豬。設定裡給「顯示遮罩範圍」開關供除錯用（`localStorage`）。
編輯器內當然一律顯示。

## 3. 通知改良

### 3.1 現況的兩個問題

1. `routers/alerts.py:29` 的 `limit` 預設 50，清單看不到更早的紀錄。
2. **未讀數也被 50 封頂**：前端 `panels.js:281` 打 `/alerts?unread_only=true`
   再算 `len()`，吃的是同一個 limit。這是 bug，不是設計。

### 3.2 折疊

同一 `camera_id` + `object_id` + `metric` 的告警，**連續且間隔小於 6 小時**者折成一條，
顯示最新時間與發生次數。間隔超過 6 小時就另起一條。

**否決**：不分時間窗，同一組合永遠折成一條。
理由是採血決策關心的是「這隻豬今天是不是又低了」，把跨天的告警折成一條會直接抹掉這個訊號。

**折疊做在後端 Python**，是一個純函式：吃一串依時間遞減排序的原始告警，吐出折疊後的群組。
SQL 只負責取原始列，分頁用 `(triggered_at, id)` 的 keyset。

**否決**：在前端折。
理由是「載入更多 50 筆」拿回來折完可能只剩 5 條，使用者會覺得按鈕壞了；
分頁的每一頁筆數必須是折疊後的筆數才講得通。

**否決（2026-08-22 修正，原本選的就是這個）**：折疊做在 SQL 的 window function。
理由是測試寫不出來：`tests/test_db_writer.py` 所有 DB 函式測試都用 `AsyncMock`，
全套件 26 個測試檔沒有任何一個連真的 postgres。用 mock 只能斷言 SQL 字串裡有 `LAG`，
證明不了它折得對；而為此引進一組需要真 DB 的測試，會讓「全套件 0 失敗」
這個乾淨的底線在沒開 container 的機器上失效。

**2026-08-22 實機修正**：第一版的 cursor 取「最後一個回傳群組的最舊成員」，在真實資料上
會讓同一筆告警出現在兩頁（`rpi5_dual` 實測重疊 2 筆）。原因是群組依「最新成員」排序，
而一個橫跨數小時的群組，它最舊的成員可能比後面好幾個群組都還舊，cursor 蓋不住它。
正確的 cursor 是「本頁所有成員裡最舊的那一筆」，而且 cursor 往舊的方向移之後，
本頁必須跟著擴張把「比 cursor 新卻排在 limit 之外」的群組收進來，否則那些群組兩頁都碰不到。
見 `alert_grouping.page_groups`。當初的單元測試沒抓到，是因為假資料裡沒有長短群組交錯。

後端 Python 折疊保住了否決前端折疊的那個理由：router 用 keyset 一直往回抓原始列，
直到湊滿「limit + 1」個折疊群組才回傳，前端拿到的永遠是滿的一頁。
抓到第 limit + 1 個群組才停，是為了確保第 limit 個群組已經完整收攏，
不會有同一個群組被切成兩頁、看起來像重複兩條的情況。

### 3.3 翻頁

「載入更多」按鈕，每次 50 條（折疊後）。

**否決**：頁碼分頁。理由是通知是時間序、只會往回看，
資料持續增加時頁碼分頁會讓同一頁的內容一直漂移。

### 3.4 新端點

`/alerts/count`，回未讀數（不受 limit 影響）。前端 badge 改打這支。

### 3.5 這一輪不做

篩選（依相機／類型／日期）與批量操作（全部標已讀、多選刪除）優先度較低，
待折疊與翻頁上線後看實際使用再決定。

## 4. 操作手冊

### 4.1 位置與形式

獨立整頁 `/manual`，從齒輪旁邊開新分頁。

**否決**：右欄第四個 tab。理由是右欄實際寬度只有幾百 px，塞長篇圖文很難讀，手機更糟。
手冊是「坐下來讀一次」的東西，不是監看時要並排看的東西。

**內容格式**：Markdown 檔存在 repo 裡，後端用 `markdown-it-py`（新增依賴）渲染成 HTML。

**否決**：手寫 HTML。理由是這份手冊之後每加一個功能就要補一段，
Markdown 讓改手冊不必碰標籤。

**否決**：送原始 Markdown 讓前端渲染。
理由是要往「零 build」的前端塞一個第三方 JS 檔，與現有檔案結構不合。

### 4.2 存取控制

`/manual` 加進 `auth_middleware.py` 的 `_PUBLIC_EXACT`，**不放進登入保護**。
登入頁上如果有人卡住，手冊正好是他該看的東西；且手冊裡不含任何場域資料。

### 4.3 範圍

兩節：

   看到紅框要做什麼、怎麼查回放、怎麼用通知。
2. **設定說明**：設定抽屜每一項的意義與後果，特別是 `hls_retention_days` 這種會刪資料的。
   遮罩因為是前端操作，歸在這一節。

**否決**：加一節維運（重啟、儲存告警、部署）。
理由是這些已經在 `service-readme.md` 與 `docs/deployment.md`，
複製一份到前端只會產生兩份會不同步的說明。
設定抽屜則不同：它長在前端上、按下去會真的改變系統行為，說明必須跟按鈕在同一處找得到。

## 5. Tooltip

### 5.1 說明模式

工具列加一個 `?` 按鈕，切換全域的「說明模式」（定義見 `CONTEXT.md`）。
開啟時整頁加一層半透明遮罩表示「現在點東西不會有事」，
點任何元件只顯示它的說明、不執行它的動作，再按一次關閉。
桌機的 hover tooltip 照常保留。

**否決**：每個元件旁邊加小 ⓘ。
理由是工具列已經很擠，塞進一倍的圖示會讓手機版面爆掉。

**否決**：觸控裝置上不給 tooltip、只靠手冊。
理由是豬場現場多半就是拿手機在看，這等於現場人員完全沒有 tooltip。

說明模式的副作用是它同時解決了「使用者怕點錯」的問題。

## 6. 實作順序

五項功能彼此獨立，**每項一條 branch，做完一項合一項、上線一次**。

| # | 工作 | 為什麼排這個位置 |
|---|---|---|
| 1 | 通知改良 | 風險最低、動到的檔案與其他四項幾乎不重疊，適合先把「本機開發 → 遠端 pull → 重啟」這條流程跑通一次 |
| 2 | 關注清單（含 bbox 顯示模式） | 純呈現層，不碰推論路徑 |
| 3 | 遮罩編輯器 | 唯一會碰推論路徑的一項，風險最高，放在流程已熟練之後 |
| 4 | Tooltip 與操作手冊 | 前面三項改完 UI 才定案，手冊此時才寫得完整 |

**否決**：一條 branch 全部做完再合。理由是遮罩碰推論路徑，出問題時不該連帶把
其他四項一起 revert。

**否決**：直接在 master 上做。理由同上。

## 7. 驗收

### 7.1 共同底線

- 全套件 `uv run pytest -p no:cacheprovider` **0 失敗**。出現失敗先假設是回歸。
- 改到的 JS 過 `node --check static/js/<file>.js`。
- 新增 DB-backed 設定照慣例改 5 處：`config.py` → `routers/settings.py`
  （`ALLOWED_KEYS` + `_NUMERIC_BOUNDS` + GET no-pool fallback dict）→ `sql/init.sql` seed
  → `static/index.html` 設定欄位 → `static/js/panels.js` 的 `loadSettings`/`saveSettings`。
- 碰 ntfy 的測試必須 `monkeypatch.setattr(main.ntfy_notifier, "notify", ...)`。
- 新測試不要硬編 camera label 或假設 `.env` 預設值，照既有的三層隔離 pattern。

### 7.2 各項的專屬驗收

**通知折疊**：單元測試直接餵假的告警串給折疊純函式。同組連續兩筆間隔 5 小時 →
折成一條、計數 2；間隔 7 小時 → 兩條；不同 `camera_id`／`object_id`／`metric` 永不互折。
分頁：router 在原始列不足時要能連續往回抓，且同一群組不會被切到兩頁。
未讀數超過 50 時 `/alerts/count` 要回真實數字。

**關注清單**：零異常時出現最低 N；有異常時最低 N 消失、只列異常；`focus_top_n = 0` 時
對照區塊整個不出現。

**遮罩**：兩種驗證都要做，缺一不可。

1. 單元測試驗證過濾函式的邊界：重疊 59% 留、61% 丟、
   跨兩個遮罩區時合計重疊怎麼算、`enabled = false` 的區域不參與。
2. 遠端實機：畫一塊**明確沒有豬**的區域，用 `tracking_logs` 查證該區域的偵測數從 N 降到 0。
   選沒有豬的區域是為了避免分不清「遮罩生效」與「豬剛好走開」。

只做單元測試不夠（證明不了它接上了推論路徑），只做實機也不夠（證明不了邊界正確）。

**手冊與 tooltip**：`/manual` 未登入可讀；說明模式開啟時點按鈕不觸發動作。
